Cost Optimization Guide

Cloud spend grows predictably when workloads scale without deliberate cost controls, and organizations routinely overpay by 30–60% through idle resources, misconfigured services, and missed commitment discounts. This guide provides actionable patterns to identify waste, right-size infrastructure, and capture commitment savings — turning cost management into a competitive advantage rather than a reactive fire drill.

Pricing models

Choosing the wrong pricing model is the single largest source of cloud waste. Understanding the trade-off between commitment length, discount depth, and workload flexibility prevents overbuying reservations while still capturing available savings.

Selecting a commitment scope

Graviton (ARM-based) instances

ARM-based instances deliver measurable savings with minimal code changes for most managed workloads. Evaluating Graviton early in the design phase compounds savings across every other pricing strategy.

AspectDetail
Price-performance gainUp to 40% better price-performance vs. comparable current-gen x86 instances
Direct cost savingsFamily, generation, Region, and software dependent; benchmark current On-Demand rates and throughput rather than assuming equal sizes are equivalent
Supported servicesEC2, RDS, ElastiCache, OpenSearch Service, EMR, Lambda (arm64)
Stacks withSavings Plans, Reserved Instances, and Spot for compounded savings
Migration effortLow for interpreted/managed runtimes (Lambda, Java, Python, Node.js); recompilation needed for native binaries

Storage pricing

Storage cannot be compared on a per-GB rate alone. Model capacity, IOPS/throughput, requests, minimum storage duration, retrieval, object metadata, snapshots/backups, replication, and data transfer for the deployment Region.

Tip

Use the AWS Pricing Calculator and current service pricing pages; rates in examples become stale and differ by Region and tier.

Right-sizing by service

Different services expose different signals of waste, and missing the right metric means missing the savings. Knowing which indicators matter per service prevents both over-trimming and performance degradation.

ServiceMetricOver-provisionedUnder-provisioned
EC2CPU, memory agent metrics, network/EBS throughput, latency, queue depth, credits, licensesResources remain idle through representative peaksSLO breaches, saturation, throttling, or insufficient burst headroom
RDSDB load/waits, CPU, memory/swap, connections, latency/queue depth, storage/I/OLow load with excess instance/storage capacity after failover headroomQuery/lock bottleneck or sustained resource pressure; fix queries before blindly scaling
LambdaDuration, errors/throttles, MaxMemoryUsed, concurrency, cold starts, cost per transactionLower memory or architecture improves tested cost without hurting SLOMore memory can also add CPU and reduce duration; use Lambda Power Tuning or equivalent testing
EBSIOPS, throughput, latency, queue length, burst balance, instance EBS limitsProvisioned performance materially exceeds measured needApproaching volume or instance limits, rising latency, or credit exhaustion
DynamoDBConsumed capacity, throttles, latency, warm/maximum throughput, table classProvisioned capacity remains unused after auto-scaling designThrottles/SLO impact, hot keys, or reactive scaling that cannot absorb peaks

Tagging strategy

Untagged resources become unallocated cost — money you cannot trace, challenge, or optimize. A consistent tagging schema is the foundation of every downstream cost governance practice.

Required tags

CostCenter

Financial tracking. Example: CC-12345

Environment

Environment classification. Example: prod, dev, staging

Owner

Team responsibility. Example: team-platform

Project

Project association. Example: project-alpha

Application

Application identification. Example: web-frontend

Compliance

Regulatory needs. Example: pci, hipaa

Tag enforcement

Tagging policies without enforcement are easily ignored, leaving cost visibility gaps. Layered enforcement ensures compliance at creation time and catches drift before it becomes unmanageable.

MethodDescription
Service Control PoliciesDeny selected create APIs when documented request-tag conditions are absent; tag-on-create support varies by service/action
AWS Config RulesDetect noncompliant tags and optionally trigger remediation; Config is not preventive by itself
CloudFormationPropagate stack tags to supported resources; not every resource supports propagation
CDK/TerraformProvider-level default tags
Tag policiesStandardize allowed tag keys/values and report compliance; enforcement support depends on resource type and mode
Note

Activate required user-defined cost allocation tags in Billing; merely attaching a resource tag does not make it appear retroactively in cost allocation reports.

EBS optimization

Block storage waste is often invisible — orphaned volumes, oversized gp2 volumes, and retained snapshots compound silently. Proactive EBS hygiene recovers cost without affecting running workloads.

Network cost optimization

Data transfer costs

Egress and cross-AZ transfer charges are the most common surprise on cloud bills. Understanding where data moves and why is the first step to eliminating hidden network spend.

Transfer typeCharging dimensionsOptimization
Internet outService, source Region, destination, tier, and free allowanceEvaluate CloudFront, compression, protocol, and response size
Cross-AZService-specific processing and data transfer on one or both sidesRemove accidental hairpins/chattiness; preserve required AZ resilience
Cross-RegionSource/destination services and Regions; managed replication may price differentlyReplicate only required data and compress/batch where supported
VPC peering / Transit Gateway / PrivateLinkArchitecture-specific hourly and per-GB processing chargesCompare total paths and operational scale; Transit Gateway is not automatically cheaper than peering
Direct ConnectPort-hour, data transfer, provider/cross-connect, and possible gateway chargesSelect capacity and resiliency from measured demand

Network optimization

Network architecture decisions have lasting cost consequences that are hard to reverse. Designing for transfer efficiency from the start avoids expensive remediation later.

StrategyDescriptionPotential savings

VPC EndpointsAvoid NAT/internet gatewayData transfer costs

Database cost optimization

RDS optimization

Database costs compound from over-provisioned instances, unnecessary Multi-AZ deployments, and retained backups. Aligning database configuration to actual availability requirements recovers significant spend.

StrategyDescriptionPotential savings
Match availability to requirementsUse Multi-AZ when the environment's availability/recovery objective requires it, regardless of the prod labelAvoid unnecessary standby capacity without weakening required resilience
Right-size instancesMatch compute, memory, storage/I/O, licenses, and replica count to workloadWorkload-dependent
Reserved DB instances / Database Savings PlansCompare matching reservations with the broader eligible database-spend commitmentOffering- and usage-dependent
Storage auto scalingPrevent storage exhaustion; it does not shrink already allocated storageReliability, not automatic savings
Snapshot retentionAutomate cleanupStorage costs

DynamoDB optimization
