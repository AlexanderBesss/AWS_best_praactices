AWS Lambda Best Practices

Design Lambda functions as short-lived, stateless compute units while taking advantage of safe execution-environment reuse. Delivery semantics, retries, and failure destinations depend on the invocation source; there is no single Lambda retry policy for every trigger.

Function design

Functions that follow disciplined design patterns are easier to test, scale, and maintain. These practices reduce coupling, surface failures early, and keep costs predictable.

ConcernBest practice
ScopeKeep one function focused on a cohesive capability and event contract
HandlerKeep orchestration thin; isolate business logic from Lambda-specific input/output for testing
IdempotencyMake side effects safe under duplicate delivery and retries; persist an idempotency key atomically
InitializationCreate SDK clients, database connections, and reusable assets outside the handler
StateTreat memory and /tmp as a cache only; never require reuse for correctness or user isolation
ConfigurationUse environment variables for non-secret settings and a managed secret store for credentials
DeploymentPublish immutable versions and route aliases to versions for production
Warning

Initialize reusable resources outside the handler, contrary to the common but harmful advice to move initialization into the handler. Validate that reused connections remain alive, and never store per-user sensitive state where a later invocation can observe it.

Configuration and quotas

Right-sizing these settings directly affects latency, throughput, and cost. Misconfigured limits cause throttling, silent failures, or unexpected bills.

SettingCurrent service boundary / guidance
TimeoutUp to 900 seconds; load test and set enough margin for dependency latency and cleanup
Memory128–10,240 MB in 1 MB increments; CPU scales with memory
CPUAt 1,769 MB a function receives the equivalent of one vCPU; at maximum memory it can receive up to six vCPUs
Ephemeral storage512–10,240 MB; storage above 512 MB is billed for invocation duration
ArchitectureBenchmark arm64 and x86_64 with the real dependencies; ensure native binaries support the target
ConcurrencyThe default regional account quota is commonly 1,000 but can be lower for new accounts and is adjustable
Environment variablesAggregate limit is 4 KB; encryption does not make them an appropriate secret-distribution mechanism
  • Use AWS Lambda Power Tuning or representative load tests to select memory from cost and latency, not rules of thumb.
  • Set reserved concurrency to reserve/cap capacity for critical functions or protect a downstream system. Reserving it unnecessarily reduces the shared unreserved pool.
  • Configure maximum concurrency on SQS event source mappings when the queue consumer must not overwhelm dependencies.
  • Confirm quotas in Service Quotas for every target Region before launch; do not assume the account default.

Cold starts and execution reuse

Cold starts and execution reuse determine the latency profile your users actually experience. Choosing the right technique depends on runtime, cost tolerance, and whether you need a guarantee.

TechniqueImportant nuance
Execution reuseMove clients/connections outside the handler and cache static assets in /tmp
Package reductionInclude only runtime dependencies; measure impact instead of assuming size is the only cold-start factor
Memory tuningMore memory adds CPU and can reduce initialization/duration, but benchmark total cost
Provisioned ConcurrencyKeeps a configured number of environments initialized; overflow beyond it can still cold start
SnapStartAvailable for supported Java, Python, and .NET managed runtimes on published versions; restore from a snapshot rather than keeping capacity provisioned

SnapStart constraints

SnapStart is incompatible with Provisioned Concurrency, EFS, S3 Files, container images, and ephemeral storage above 512 MB. Initialization state is cloned, so reseed uniqueness, refresh credentials/connections, and use runtime hooks where needed. Availability, supported runtime versions, Regions, and pricing evolve; verify them before standardizing.

VPC networking

VPC attachment is no longer accurately described as creating a new ENI for every cold start; Lambda uses Hyperplane ENIs. Put a function in a VPC only when it needs VPC resources — see VPC Best Practices for designing that connectivity. A VPC-connected function does not retain default internet access—provide NAT or appropriate VPC endpoints. Endpoints improve private connectivity and security, not cold-start initialization by themselves.

Tip

Scheduled “keep warm” invocations are not a dependable cold-start guarantee and create noise/cost. Use Provisioned Concurrency when a guarantee is required.

Invocation and retry semantics

Different invocation sources handle failures independently, so understanding each path is essential to avoid duplicate processing or swallowed errors. For broader patterns around retries and dead-letter handling, see Error Handling Patterns.

Invocation pathFailure behavior
Synchronous (RequestResponse)Lambda returns the error; the caller/source decides whether to retry
Asynchronous (Event)Lambda queues the event and by default retries function errors twice; maximum event age, retry attempts, destinations, and DLQ are configurable
SQS event source mappingLambda polls; failed messages become visible after the queue visibility timeout and the queue redrive policy controls movement to its DLQ
Kinesis/DynamoDB stream mappingFailed batches can block a shard; configure partial failures, bisect, maximum record age/retries, and an on-failure destination as appropriate
Kafka/MQ/document DB mappingsSource-specific polling, batching, and retry semantics apply; consult the trigger guide

An asynchronous Lambda DLQ/destination is different from an SQS source queue's DLQ and from an event source mapping's on-failure destination. Prefer destinations for asynchronous invocations when you need richer success/failure records and routing. For event-driven triggers such as EventBridge or API Gateway, check the trigger-specific guidance as well.

  • Use exponential backoff with jitter for retrying SDK calls and bound attempts by the remaining function time.
  • Apply circuit breaking/load shedding when retries would amplify a failing dependency.
  • Distinguish retriable errors from invalid/poison events and include enough metadata for safe remediation.
  • Never assume exactly-once execution. Use conditional writes, transactions, deduplication records, or an idempotency utility.

SQS event source mappings

SQS mappings introduce their own retry and visibility mechanics that must align with function timeout and batch size to avoid message loss or infinite loops.

SettingGuidance
Batch sizeStandard queues support up to 10,000 records; FIFO queues up to 10; payload size can reduce the actual record count
Batch windowStandard queues only; if batch size exceeds 10, configure at least one second
Visibility timeoutAt least six times the function timeout, plus the batching window, per Lambda guidance
Queue redriveConfigure a queue DLQ and set maxReceiveCount to at least 5 unless evidence supports another value
Partial failuresEnable ReportBatchItemFailures and return only failed message identifiers
ScalingUse event-source maximum concurrency and reserved concurrency deliberately; preserve capacity for other functions
Note

Delete/acknowledge behavior is controlled by the event source mapping. Do not manually delete each SQS message from a normally successful Lambda batch. For FIFO queues, stop processing after the first failure and report failed/unprocessed records to preserve ordering.

Security

Lambda functions inherit the blast radius of their execution role, so least-privilege access and secret hygiene are non-negotiable. Role design follows IAM Best Practices, and key management follows KMS Best Practices.

ControlRecommendation
Execution roleGrant only actions/resources the function needs; separate deployment permissions from runtime permissions
Resource policyRestrict who/services can invoke the function, including SourceArn/SourceAccount where supported
SecretsUse Secrets Manager or Parameter Store SecureString, cache with bounded lifetime, and rotate
Environment variablesStore non-secret configuration; use a customer managed KMS key only when key-policy control is required
VPCUse for private dependencies, with least-privilege security groups and required NAT/endpoints
Supply chainPin/scan dependencies, use trusted base images, and sign supported ZIP deployments when required
LogsPrevent credentials, tokens, and sensitive payloads from entering logs; set retention and access controls

Lambda code signing validates signed ZIP deployment packages from trusted AWS Signer profiles; it does not apply to container-image functions. Scan both application packages and layers, and patch shared layers/runtimes promptly.

Packaging and deployment

Package format and deployment strategy affect cold-start performance, supply-chain risk, and rollback capability.

PackageLimits and guidance
ZIP archiveDirect API/console upload is limited to 50 MB zipped; the unzipped function plus layers and custom runtime is limited to 250 MB
LayersUp to five layers per function; they count toward the 250 MB unzipped total
Container imageUp to 10 GB uncompressed; image must be in an Amazon ECR repository in the same Region
  • Use infrastructure as code (SAM, CDK, CloudFormation, or another controlled tool) and deploy immutable versions.
  • Shift an alias gradually with CodeDeploy/SAM and alarms that stop/roll back a deployment.
  • Layers can reduce duplication but create dependency/version coupling; do not update consumers implicitly.
  • Container images are not automatically better for cold starts. Keep them minimal, pin by digest/version, and scan ECR.
  • Set runtime-management policy deliberately and track runtime deprecation dates.

Observability

Emit structured logs with service/function name, version, cold-start indicator, request/event ID, correlation ID, and business outcome. Use Embedded Metric Format or Powertools where appropriate to avoid high-cardinality custom metric dimensions. For log/metric design, see CloudWatch Best Practices, and for distributed tracing, X-Ray Best Practices.

These metrics are the primary signals for detecting capacity pressure, latency degradation, and terminal failures before they impact users.

SignalWhat it reveals
Errors / InvocationsFunction error rate
DurationTail latency and proximity to timeout
ThrottlesAccount/function concurrency pressure
ConcurrentExecutions / ClaimedAccountConcurrencyCapacity consumption and reservation pressure
ProvisionedConcurrencySpilloverInvocationsTraffic exceeding provisioned capacity
AsyncEventAge / AsyncEventsDroppedBacklog or expiry for asynchronous invocation
IteratorAgeLag for stream event source mappings
SQS ApproximateAgeOfOldestMessageVisibleQueue backlog age; this is an SQS metric, not a Lambda metric
Destination/DLQ metricsTerminal delivery failures and remediation backlog
Note

Init Duration appears in platform logs and telemetry but is not a standard Lambda CloudWatch metric named InitDuration. Use logs, Lambda Insights, or telemetry tooling for cold-start analysis. Build thresholds from SLOs and dependency limits rather than universal percentages.

  • Use tracing selectively and propagate trace/correlation context across asynchronous boundaries.
  • Alarm on error-budget burn, throttles, oldest-event age, destination failures, and concurrency saturation.
  • Set explicit log retention; default infinite retention can become both a cost and data-governance problem.
  • Monitor recursive loops and set reserved concurrency to zero as an emergency circuit breaker when needed.

Cost and performance

Lambda cost can include requests, duration, memory architecture, ephemeral storage, Provisioned Concurrency, SnapStart for applicable runtimes, streaming, logs, data transfer, and connected services. Prices and free tiers vary.

  • Optimize at representative load: increasing memory can lower duration enough to reduce total cost.
  • Batch records where latency and failure isolation permit.
  • Use Compute Savings Plans for eligible steady Lambda duration/Provisioned Concurrency usage when commitment is justified.
  • Remove unused function versions and layer versions; they consume regional code storage even when not invoked.
  • Compare Lambda with container/batch services for long-running, constantly busy, GPU, specialized networking, or highly stateful workloads.

Lambda with Step Functions

Combining Lambda with Step Functions shifts orchestration complexity out of function code, making workflows observable, recoverable, and auditable.

DecisionRecommendation
OrchestrationUse Step Functions for multi-step workflows, branching, waits, human approval, and recovery state
Service integrationsCall AWS services directly from the state machine when custom Lambda logic adds no value
PayloadKeep state below the workflow quota; put large data in S3/DynamoDB and pass a reference
Error handlingCentralize workflow-level Retry/Catch; keep function-internal retries bounded to transient downstream calls
Workflow typeStandard for durable, auditable, long-running execution; Express for high-volume, short-duration work after evaluating its execution semantics
TasksMake every Lambda task idempotent because a state can be retried
