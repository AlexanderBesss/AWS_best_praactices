AWS KMS Best Practices

AWS Key Management Service (AWS KMS) protects key material and performs cryptographic operations on your behalf. Treat it as a dedicated encryption service — not a general-purpose secret store — and use it to protect values that live in AWS Secrets Manager or Systems Manager Parameter Store.

Choose the right key type

Selecting the correct key type determines which cryptographic operations are available and prevents architectural mismatches later.

Key typeSupported operationsTypical use
Symmetric encryptionEncrypt, decrypt, re-encrypt, and generate data keysDefault choice for envelope encryption and most AWS service integrations
AsymmetricEncrypt/decrypt, sign/verify, or key agreement, depending on KeyUsage and KeySpecWorkloads that require a public key or signatures outside AWS KMS
HMACGenerate and verify MACsMessage authenticity and integrity

Key ownership model

AWS owned or AWS managed

Prefer these when you do not need to control key policy, lifecycle, rotation, or cross-account access. They remove operational burden for standard service integrations.

Customer managed

Use a customer managed key when you need those controls, a distinct audit boundary, imported key material, a custom key store, or a multi-Region key.

Tip

Use aliases in application configuration so that manual key replacement does not require distributing a new key ARN. Use a key ARN only when a policy or API specifically requires an unambiguous key identity.

Note

Treat multi-Region keys as interoperable copies of the same key material, not as backups. Each replica has its own key policy, grants, aliases, tags, and regional availability.

Key states

Warning

Compromised is not an AWS KMS key state. Investigate suspected compromise, stop new use, and replace the key according to the incident plan.

Recognizing key states early prevents failed operations and guides the correct remediation path.

StateMeaningOperational response
EnabledCryptographic operations are availableNormal operation
DisabledCryptographic operations failRe-enable only after confirming that use is intended
PendingDeletionKey is in the configurable 7–30 day waiting periodAlarm on attempted use; cancel deletion if dependencies remain
PendingImportImported key material is absent or expiredImport valid key material before use
UnavailableA custom key store is disconnectedRestore the custom key store and its dependencies

Authorization and key policies

Every KMS key has exactly one key policy. In the key-owning account, an IAM policy can grant access only when the key policy delegates permission management to the account; a key policy can also grant a principal directly. Explicit denies still win.

Note

For cross-account use, the key policy in the key-owning account and an IAM policy in the caller's account are both required. See IAM Best Practices for how to structure the caller-side policies.

Proper authorization separates administrative power from routine use and keeps the blast radius of a compromised credential small.

The three authorization mechanisms

Key policy

Exactly one per key. It can grant a principal directly or delegate permission management to the account, which is what allows IAM policies to grant access.

IAM policy

Attached to users or roles. Effective on a key only when the key policy delegates permission management to the account — or across accounts, alongside the key policy.

Grant

A temporary or delegated authorization, commonly created by integrated AWS services on a caller's behalf. Grants feed into the same conditions and explicit-deny evaluation as policies.

ControlBest practice
Key administratorsUse dedicated roles; do not give application roles administrative or deletion permissions
Key usersGrant only the required cryptographic operations and resources
Account principalUnderstand that arn:aws:iam::<account-id>:root delegates authority to the account; it does not mean only the root user
Service accessRestrict with kms:ViaService, encryption-context conditions, and source-account/source-ARN conditions where supported
DeletionSeparate kms:ScheduleKeyDeletion and kms:CancelKeyDeletion from routine administration; require change control
Policy safetyKeep a recoverable administrator path and do not bypass the policy lockout safety check without a controlled reason

Common application permissions

Mapping permissions to encryption patterns avoids overprivileged roles and makes access reviews faster.

PatternCommon permissions
Encrypt a small payload directlykms:Encrypt, often kms:DescribeKey
Decrypt existing ciphertextkms:Decrypt, often kms:DescribeKey
Envelope encryptionkms:GenerateDataKey to encrypt; kms:Decrypt to recover the data key
Re-encrypt without exposing plaintextkms:ReEncryptFrom on the source and kms:ReEncryptTo on the destination
Service integrationService-specific permissions; some services create grants on the caller's behalf
Warning

Avoid granting kms:CreateGrant broadly. When it is necessary, use kms:GrantIsForAWSResource, grant-operation conditions, and a specific grantee.

Envelope encryption

Use data keys for payloads larger than the KMS API plaintext limit and for high-throughput encryption. Store the encrypted data key with the ciphertext and erase the plaintext data key from memory as soon as practical.

Warning

The encryption context is authenticated but not encrypted, so never put secrets in it. It binds ciphertext to its purpose, not protects it.

  • Use the AWS Encryption SDK or an AWS service integration instead of designing a custom envelope format.
  • Encryption context must match exactly for decrypt operations. Log and document the context schema.

Rotation and replacement

Choosing the right rotation strategy balances forward secrecy with operational complexity and decryptability of existing data.

MethodApplies toBehavior
Automatic rotationCustomer managed, symmetric encryption keys with AWS_KMS key materialDefault period is 365 days; configurable from 90 through 2,560 days
On-demand rotationSupported customer managed symmetric encryption keys with AWS_KMS or EXTERNAL originRotates backing material without changing the key ID or re-encrypting existing ciphertext
Manual replacementAll key typesCreate a new key, move aliases/configuration, and optionally re-encrypt data

AWS managed keys rotate automatically every year and cannot be configured by customers. Automatic and on-demand rotation retain old backing material so existing ciphertext remains decryptable.

Warning

Rotation does not mitigate compromised plaintext, excessively broad access, or leaked data keys. Use manual replacement and re-encryption when the risk assessment requires a new key boundary.

Grants

Grants are commonly used by integrated AWS services for temporary or delegated access. They are eventually consistent; use a grant token when the new grant must be used immediately.

Tight grant constraints limit what a principal can do with the key and for which data, reducing the impact of misuse.

ControlRecommendation
OperationsInclude only the operations the grantee requires
GranteeUse a specific role or supported service principal
EncryptionContextEqualsRequire an exact encryption context for supported symmetric operations
EncryptionContextSubsetRequire named context pairs while allowing additional pairs
Source ARN constraintRestrict use to requests made for a specific AWS resource when supported
LifecycleRetire temporary grants; reserve revoke for key administrators
Note

RetiringPrincipal and the grant ID identify and manage a grant; they are not grant constraints.

Monitoring and incident readiness

Monitoring KMS activity surfaces policy changes, misuse, and infrastructure failures before they cause data loss or outages. Pair these signals with the broader alerting approach in CloudWatch Best Practices.

SignalWhat to monitor
CloudTrailKey creation, policy changes, grants, enable/disable, rotation settings, imported material, and deletion scheduling/cancellation
KMS SuccessfulRequest metricSuccessful cryptographic operations by key and operation; detect unexpected use and quota/cost growth
Imported materialSecondsUntilKeyMaterialExpiration and alarms well before expiry
Custom key storesThrottling, proxy errors/latency, certificate expiry, credentials, and external key-manager health
Service QuotasRequest-rate utilization and throttling
  • Create high-severity alerts for PutKeyPolicy, ScheduleKeyDeletion, DisableKey, DeleteImportedKeyMaterial, and unexpected CreateGrant calls.
  • Maintain an inventory of key owners, dependent services, aliases, policy purpose, rotation method, and recovery/runbook links.
  • Before scheduling deletion, disable the key, monitor attempted use, inventory grants and aliases, and retain the full waiting period appropriate to the workload.
  • Test encrypted-data recovery, including cross-account and multi-Region failure scenarios. A KMS key cannot be exported as a backup.

Cost and scale

KMS prices and free tiers vary by key type, operation, and Region. Use the current pricing page instead of embedding dollar amounts in architecture standards; see the Cost Optimization guide for how to keep service costs under review.

  • Consolidate keys only when tenants, data classifications, administrators, retention, and blast-radius requirements permit it.
  • Cache data keys only with a bounded age/use count and an approved cryptographic materials cache.
  • Use GenerateDataKeyWithoutPlaintext when a component should provision encrypted data keys but must not receive plaintext key material.
  • Review KMS request quotas before high-throughput launches and use envelope encryption to avoid a KMS call per data block.
