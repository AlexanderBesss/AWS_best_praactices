AWS Shield Best Practices

AWS Shield protects AWS-hosted applications from distributed denial-of-service (DDoS) attacks. It complements — and never replaces — AWS WAF, resilient architecture, capacity planning, and an incident-response process.

Shield Standard vs Shield Advanced

Understanding the capability gap between the free tier and the paid tier prevents over-provisioning and ensures cost protection is available where it matters.

CapabilityShield StandardShield Advanced
EnrollmentIncluded automatically with AWS accountsPaid subscription with a commitment; enroll and protect resources explicitly
Core protectionAutomatic network and transport-layer DDoS detection and inline mitigation for supported AWS servicesEnhanced detection and mitigation, visibility, health-based detection, and protected-resource controls
Application layerUse AWS WAF separatelyAWS WAF is central to layer 7 protection; automatic application-layer DDoS mitigation is available for eligible CloudFront and ALB protections
VisibilityService-level protections with limited customer event detailDDoS event diagnostics, CloudWatch metrics, dashboards, and notifications
Response supportNormal AWS Support pathShield Response Team (SRT) assistance when support-plan prerequisites are met
Cost protectionNot includedDDoS cost protection for eligible scaling charges, subject to prerequisites and credit approval
Organization managementNot applicableAWS Firewall Manager can apply policy centrally to supported resource types
Warning

Do not describe Shield Advanced as protecting against every attack. It focuses on DDoS; injection, credential abuse, authorization flaws, malware, and data exposure require other controls.

When Shield Advanced is a good fit

Critical availability

Internet-facing workloads where availability has a material business or safety impact.

Targeting history

Applications with a high likelihood or history of DDoS targeting.

Response and visibility needs

Organizations that need SRT engagement, detailed DDoS visibility, or DDoS cost protection.

Multi-account estates

Estates that need centrally governed protection through AWS Firewall Manager.

Evaluate the current subscription, support-plan, WAF, and cost-protection requirements before purchasing. "Public-facing" alone does not make Shield Advanced mandatory.

Supported resources and scope

Shield Standard protections apply automatically to supported AWS edge and regional entry points. Shield Advanced can create explicit protections for the following resource types documented by AWS. Mapping each entry point to the correct protection model ensures no internet-facing asset is left outside the DDoS defense perimeter.

ResourceShield Advanced guidance
CloudFront distributionPreferred public HTTP(S) entry point; associate AWS WAF and consider automatic application-layer DDoS mitigation — see CloudFront Best Practices
Route 53 hosted zoneProtect authoritative DNS and monitor DNS-query health — see Route 53 Best Practices
Global Accelerator standard acceleratorUse for static anycast entry points and origin shielding for supported endpoints
Elastic IP addressProtect the EIP and the resource exposed through it
Application Load BalancerProtect the ALB; associate a regional web ACL for layer 7 controls — see Load Balancing Best Practices
Classic Load BalancerExplicitly protect when still required; prefer modern load balancers for new designs
Network Load BalancerProtect through its associated Elastic IP addresses; AWS WAF does not associate with NLBs
Note

A VPC, EC2 instance without an eligible entry-point resource, web ACL, or API Gateway API is not itself a Shield Advanced protected-resource type. API Gateway can be protected at layer 7 with AWS WAF (REST APIs) or placed behind CloudFront where appropriate.

Warning

Shield Advanced resource protection supports IPv4, not IPv6. If the application accepts IPv6, document the exposure and verify the current service behavior and compensating edge architecture.

Layered DDoS-resilient architecture

A defense-in-depth approach distributes DDoS controls across every network hop so no single layer becomes the failure point.

LayerControls
Edge and DNSRoute 53, CloudFront, Global Accelerator, anycast ingress, and Shield
Network/transportShield mitigation, NLB/ALB, security groups, and minimal exposed ports
ApplicationAWS WAF managed/custom rules, rate-based rules, CAPTCHA/Challenge, caching, and origin protection
Capacity and healthAuto Scaling, resilient multi-AZ origins, dependency limits, Route 53 health checks, and load shedding
OperationsMetrics, alarms, SNS notifications, runbooks, AWS Support/SRT access, and game days

Design practices

  • Hide and restrict origins. For CloudFront origins, allow only CloudFront-originated traffic using supported managed prefix lists, secret headers where appropriate, or service-specific origin access controls.
  • Cache safe content at CloudFront to absorb request volume before it reaches the origin.
  • Set WAF rate limits from measured legitimate traffic and test rules in Count mode before enforcing them — see WAF Best Practices.
  • Protect dependencies from a successful traffic surge using queues, concurrency controls, circuit breakers, and admission control.
  • Avoid relying on network ACLs as a dynamic DDoS control; they are stateless, coarse, and operationally difficult to change during an event.

Shield Advanced setup

Following a structured setup sequence prevents gaps between subscription activation and actual resource protection.

StepBest practice
Subscription ownershipUse a designated security account and document the payer/commitment model
Protection coverageInventory every eligible internet-facing entry point and automate association for new resources
Protection groupsGroup resources that share a workload so events and health can be evaluated coherently
Health checksAssociate meaningful Route 53 health checks where supported; health-based detection depends on accurate signals
Application-layer mitigationFor eligible CloudFront/ALB protections, enable automatic mitigation only after the associated web ACL and baseline are ready
SRT accessProactively authorize the SRT to inspect and update WAF protections; confirm required AWS Support plan
NotificationsConfigure Shield Advanced SNS event notifications and CloudWatch alarms — see CloudWatch Best Practices
Organization rolloutUse Firewall Manager for supported resources; manage Route 53 and Global Accelerator protections separately because Firewall Manager Shield policies do not support them

Detection, response, and testing

The event flow below covers detection through post-incident review, including where the Shield Response Team fits in.

Before an event

  • Record resource ARNs, application owners, support contacts, escalation severity, and the AWS Support case procedure.
  • Confirm SRT authorization rather than waiting for an incident.
  • Run controlled game days. Do not generate DDoS traffic or use a load-testing vendor without following AWS's DDoS simulation testing policy and obtaining any required approval.
  • Test alarms against application health degradation as well as traffic volume.
Tip

During an event, Shield mitigation is automatic. Contact AWS Support when application health is affected, mitigation needs tuning, the event is not visible, or you require SRT assistance. Preserve timestamps, resource ARNs, health symptoms, request samples, and WAF logs.

Monitoring

Shield Advanced publishes metrics in AWS/DDoSProtection. Global-service and protection-group metrics are reported in us-east-1; regional-resource metrics are reported in the resource's Region. Aligning the right metric to the right alarm turns raw DDoS telemetry into actionable incident signals.

MetricUse
DDoSDetectedAlarm when nonzero, then correlate with health and traffic; nonzero does not by itself prove customer impact
DDoSAttackBitsPerSecondNetwork/transport event volume in bits per second
DDoSAttackPacketsPerSecondNetwork/transport event packet rate
DDoSAttackRequestsPerSecondApplication-layer request-flood rate when available
VolumePacketsPerSecond / VolumeBitsPerSecondMitigation and top-contributor visibility with the documented dimensions

Also monitor ALB/CloudFront/Route 53 health, origin latency/error rates, WAF AllowedRequests, BlockedRequests, CountedRequests, and dependency saturation. Shield metrics are more frequent during an event and otherwise can be reported only periodically, so they should not be the sole application-health signal.

Cost protection and pricing

Shield Advanced pricing, data-transfer inclusions, and DDoS cost-protection eligibility can change and differ by resource or agreement. Use the current pricing and cost-protection pages instead of embedding packet, bandwidth, or regional prices.

Note

To remain eligible for DDoS cost protection, follow the documented architecture and operational prerequisites, including appropriate Shield Advanced protection, WAF protection for application-layer resources, and timely SRT engagement where required. Cost protection is a credit process, not automatic reimbursement for every charge.
