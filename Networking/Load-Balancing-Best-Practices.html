Choosing the right load balancer

The four load balancer families optimize for different jobs. Match your traffic protocol, routing needs, and performance requirements before you commit to a design.

Application LB (ALB)

Layer 7 content-aware HTTP/HTTPS routing with host and path rules, native WebSocket and gRPC support. Current generation.

Network LB (NLB)

Layer 4 TCP/TLS/UDP routing at very high performance, with static Elastic IP addresses for stable entry points. Current generation.

Gateway LB (GWLB)

Transparent insertion of third-party network virtual appliances (firewalls, IPS) using GENEVE encapsulation. Current generation.

Classic LB (CLB)

Previous-generation layer 4/7 load balancing. Migrate workloads to ALB or NLB where practical.

Health check best practices

These practices ensure health checks accurately reflect application state without introducing instability or cascading failures.

PracticeDescription
Dedicated endpoint/health or /ping endpoint
Lightweight checkMinimal processing
Check dependenciesUse a shallow liveness endpoint for process health and a carefully designed readiness endpoint for essential dependencies; avoid cascading eviction
Graceful degradationMark unhealthy before crash
Drain connectionsDeregistration delay for graceful shutdown
Tip

Keep liveness and readiness concerns separate: a shallow endpoint that verifies the process is alive, plus a carefully designed readiness check for essential dependencies. Overly deep dependency checks cause cascading eviction during partial outages.

Routing rules & sticky sessions

ALB routing

ALB routing rules enable content-based traffic distribution, allowing a single load balancer to serve multiple services or versions based on request attributes.

Rule TypeDescriptionExample
Host-basedRoute by hostnameapi.example.com to API
Path-basedRoute by URL path/api/* to API backend
Header-basedRoute by HTTP headerCustom-App: v2 to v2 backend
Query stringRoute by query params?version=2 to v2 backend
HTTP methodRoute by methodPOST to write backend

Sticky sessions

Sticky sessions bind a client to a specific target for a duration. They should be used sparingly since they reduce load distribution effectiveness and complicate scaling.

SettingRecommendation
Cookie-basedApplication or LB-generated
DurationMinimum needed
When to useStateful applications only
AlternativeExternal session store (ElastiCache)
Tip

Prefer an external session store such as ElastiCache over sticky sessions wherever possible. External stores keep targets stateless, preserve even load distribution, and simplify scaling.

Capacity-unit billing

ALB, NLB, and GWLB capacity-unit formulas use different dimensions, and allowances can vary by protocol, certificate/key size, and feature. Billing uses the highest applicable dimension for the hour rather than summing all dimensions.

Warning

Do not hard-code LCU/NLCU/GLCU allowances in designs. Use the current ELB pricing page and CloudWatch consumed-capacity metrics, because formulas and allowances change over time.

Additional best practices

  • Enable at least two Availability Zones and maintain enough healthy target capacity in each zone for the selected cross-zone behavior. See High Availability & DR Patterns for broader resilience guidance.
  • Set deregistration delay and application shutdown handling together so deployments and scale-in drain requests cleanly.
  • Preserve the client IP only when required and understand the NLB protocol/target-type defaults; otherwise use Proxy Protocol v2 only when the target explicitly supports it.
  • Protect internet-facing ALBs with AWS WAF where appropriate (see WAF best practices), restrict security groups, and use Shield protections according to the threat model.
  • Use zonal shift/autoshift only for supported resources and rehearse the capacity impact of evacuating an Availability Zone.
