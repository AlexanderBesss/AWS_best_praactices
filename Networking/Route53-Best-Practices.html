Route 53 Best Practices

Health Checks

Health checks are the mechanism Route 53 uses to determine whether an endpoint is serving traffic, so selecting the right type matters for accuracy and cost.

Health check types

Endpoint

HTTP/HTTPS, TCP, or HTTPS with string matching. Best for application health.

CloudWatch Alarm

Based on a CloudWatch metric. Best for custom health criteria.

Calculated Health Check

Combine multiple child health checks with AND/OR/NOT logic. Best for complex health logic.

Health check configuration

These settings control how Route 53 probes your endpoints; tuning them balances detection speed, accuracy, and cost.

Alias vs CNAME

An alias is a Route 53 record feature on supported record types (usually A/AAAA), not a DNS record type of its own. Understanding the trade-offs between alias and CNAME helps you minimize extra queries and cost while maintaining flexibility.

FeatureAliasCNAME
Zone apexSupportedNot supported
Additional queriesNo (resolved by Route 53)Yes (additional DNS query)
CostRoute 53 does not charge for alias queries to eligible AWS resources; target-service charges can still applyStandard Route 53 query charges apply
Health checksCan evaluate target health for supported alias targets, or use an explicit health check where supportedUse routing-policy records and health checks rather than relying on the CNAME itself
AWS resourcesELB, CloudFront, S3, etc.Any hostname
RecommendationPrefer Alias for AWS resourcesUse for non-AWS targets
Tip

Prefer alias records for eligible AWS resources (ELB, CloudFront, S3, and similar targets). They resolve without an extra DNS query, work at the zone apex, and are not charged by Route 53 as queries.

DNSSEC

DNSSEC adds cryptographic signatures to DNS responses; the settings below define how keys are managed and rotated. The customer-managed KSK relies on KMS Best Practices.

DNSSEC configuration

SettingRecommendation
Enable DNSSECFor public zones when the registrar/parent-zone chain of trust and operations are ready; test rollover and failure recovery
Key signing key (KSK)Backed by a customer-managed asymmetric KMS key in us-east-1; you manage KSK lifecycle
Zone signing key (ZSK)Managed by Route 53
Key rolloverPlan KSK rollover; Route 53 manages ZSK rotation
Trust anchorDS record at registrar
VPC resolver validationEnable Route 53 Resolver DNSSEC validation separately for VPCs that require validation; authoritative signing and recursive validation are different controls

Benefits

DNSSEC addresses core trust concerns in the DNS ecosystem by providing verifiable response authenticity.

Authenticity

Verify response source.

Integrity

Detect tampered responses.

Denial of existence

Prove a record does not exist.

Compliance

Meet security requirements.

Warning

Do not enable DNSSEC signing without completing the parent-zone DS chain, and enable alarms for DNSSECInternalFailure and DNSSECKeySigningKeysNeedingAction.

Amazon Application Recovery Controller (ARC)

ARC is a separate AWS service for recovering applications across Availability Zones and Regions. Routing controls integrate with a special Route 53 health check, but ARC also includes non-DNS recovery capabilities. Each component addresses a different failure scope, from single-AZ impairment to full regional failover.

Components

ComponentDescriptionUse case
Region switchOrchestrate and monitor multi-Region recovery plans with plan evaluation and execution safety controlsManaged regional failover workflow
Routing controlsHighly available on/off switches (backed by a 5-endpoint redundant cluster) that gate traffic shiftingDeterministic, low-latency failover trigger
Readiness checks (existing customers)Audit resource configuration/capacity/quota parity across replicas; this feature is no longer open to new customersExisting recovery-group/cell designs
Zonal shift / zonal autoshiftShift traffic away from an impaired AZ (via ELB/ASG) in minutes, with optional automatic shiftFast AZ-level mitigation without a full DR failover

ARC best practices

These practices ensure ARC-driven failover is tested, observable, and aligned with real DNS behavior.

PracticeDescription
Use routing controls for operator-controlled regional failoverRouting controls provide a highly available control plane and safety rules, but DNS caching and record TTLs still affect when clients observe DNS changes
Evaluate recovery plans continuouslyFor new designs, use Region switch plan evaluation; existing readiness-check customers can continue using readiness checks
Test zonal shift regularlyValidates AZ-level mitigation without waiting for a real incident
Note

ARC readiness checks are no longer open to new customers. For new designs, use Region switch plan evaluation instead; existing readiness-check customers can continue using readiness checks.

Additional Best Practices

  • Use alias A and AAAA records for supported dual-stack AWS targets and keep IPv4/IPv6 health and routing behavior consistent.
  • For failover records, understand the "all records unhealthy" behavior and avoid attaching a health check to an alias when EvaluateTargetHealth already represents the same target state.
  • Keep TTLs low enough for the recovery objective before a planned migration, then raise them when stability and cache efficiency matter. Existing cached answers remain until their TTL expires.
  • Protect hosted-zone and registrar changes with least privilege, MFA for human access, CloudTrail alerts, and registry/registrar lock where available.
  • Enable DNSSEC alarms for DNSSECInternalFailure and DNSSECKeySigningKeysNeedingAction; do not enable signing without completing the parent-zone DS chain.
  • Use Resolver endpoints and rules for hybrid DNS; do not forward private DNS through an internet NAT path.
