X-Ray Best Practices

Distributed tracing is critical for modern microservice architectures because requests span multiple services, making it impossible to pinpoint latency, errors, or bottlenecks by examining individual components in isolation. Capturing the full lifecycle of a request across all downstream dependencies provides end-to-end visibility that enables faster root-cause analysis, informed capacity planning, and reliable SLO tracking.

Architecture

AWS X-Ray captures segments from your application and its dependencies, stores them in the X-Ray service, and renders them as a service map, trace graph, groups, and insights. Understanding each building block and its role is essential for proper architecture, troubleshooting, and planning the migration from legacy X-Ray SDKs to OpenTelemetry.

Important (2026)

AWS X-Ray SDKs and Daemon are in maintenance mode (security fixes only). For new projects, use AWS Distro for OpenTelemetry (ADOT) / OpenTelemetry as the recommended instrumentation approach. Existing X-Ray deployments should plan migration to OpenTelemetry.

Trace sampling

Sampling directly balances observability against cost and overhead, so getting the rates right is essential for sustainable production tracing.

SettingRecommendationReason
Default rateFirst request/sec (reservoir) + 5% of additional requestsBalance cost and coverage
Reservoir size1 request/sec (default)Sets the sampling quota before the additional percentage rate; it is not a traffic-independent guarantee
Custom rulesPer-service ratesFocus on critical paths
ProductionSet rates per route from traffic volume, incident-detection needs, and trace budgetCost and coverage control
Debugging100% temporarilyFull visibility
Note

The default rule is a baseline, not a universal production target. With centralized sampling, X-Ray coordinates reservoir allocation across clients; local sampling rules can apply a reservoir per process and therefore sample more traffic as the fleet grows.

Groups & insights

Trace groups

An X-Ray group is a named filter expression, not a separate trace copy. Filter criteria can combine service/resource fields, annotations, HTTP attributes, response time, and error/fault flags. Filter expressions are the mechanism that turns raw trace volume into focused, queryable views aligned with how your team investigates incidents.

Filter criterionUse case
Service/resourceService-level analysis
AnnotationBusiness or tenant grouping using indexed, low-cardinality values
HTTP URL pathAPI analysis
Fault/error/response timeIncident-focused analysis

Insights

Automated anomaly detection surfaces problems before they cascade, but scoping insights to relevant groups prevents alert fatigue and unnecessary cost.

Data retention & cost

Retention options

Note

X-Ray trace and service-graph data is retained for 30 days (fixed, non-configurable). If longer retention is required, design a separate telemetry export/archive path; X-Ray does not provide a retention setting that extends this window.

Planning around the fixed 30-day window early avoids last-minute data loss and ensures compliance or postmortem requirements are met.

DurationDescriptionUse case
30 daysDefault and only retention periodStandard monitoring, trend analysis
Custom retrieval/export before expiryUse X-Ray APIs or an observability pipeline designed for the required destinationLong-term archival
Parallel OpenTelemetry exportSend spans to additional approved backends through a collectorSearch or retention requirements beyond X-Ray

Cost considerations

Tracing cost scales with data volume, so understanding the cost drivers enables teams to maintain visibility without exceeding budget.

FactorImpactOptimization
Retention periodFixed at 30 days in X-RayDesign external retention only when required
Sampling rateHigher = more dataAdjust by environment

Additional best practices

  • Propagate W3C trace context across synchronous and asynchronous boundaries, and verify propagation during integration tests.
  • Put searchable, low-cardinality business attributes in annotations; put diagnostic detail in metadata. Never record secrets, tokens, full request bodies, or unnecessary personal data.
  • Tailor sampling rules by service and route. Keep enough baseline sampling for low-volume critical paths and temporarily raise sampling during a bounded investigation.
  • Monitor collector/agent health, rejected spans, exporter failures, and IAM/network access. A healthy application with a broken telemetry pipeline can otherwise look like a traffic drop.
  • Correlate logs with trace and span IDs and use CloudWatch Application Signals when service-level objectives and service discovery are required.
