CloudWatch Best Practices

Observability is the foundation of reliable cloud operations: without it, incidents go undetected until users are impacted, recovery times balloon, and root-cause analysis becomes guesswork. CloudWatch provides the metrics, logs, alarms, and signals needed to detect, diagnose, and resolve issues before they affect business outcomes.

Metrics

Choosing the right metric type balances cost, resolution, and the specificity needed to diagnose issues. Knowing which signals matter per service prevents both monitoring gaps and alert noise.

Metric resolution and retention

CloudWatch retains all metric data, but the queryable resolution degrades over time as data ages — it is aggregated to coarser periods, not deleted.

Data point periodAvailable at that resolution forCost
< 60 seconds (high-resolution)3 hoursCustom metric/API charges apply
60 seconds (1 minute)15 daysDepends on the metric source
300 seconds (5 minutes)63 daysDepends on the metric source
3600 seconds (1 hour)455 days (15 months)Depends on the metric source
Note

After each window, data is automatically aggregated to the next coarser period rather than discarded. Total retention is 15 months, but only at 1-hour resolution — plan dashboards and investigations accordingly.

Log Anomaly Detection

ML-based anomaly detection surfaces deviations from normal log patterns without requiring manual threshold tuning. Properly scoping and training anomaly detectors prevents false positives and ensures the ML model reflects actual application behavior.

Machine learning detection

FeatureDescription
Anomaly detectionML-based log pattern analysis
Pattern extractionGroups static and variable portions of log messages
Continuous detectorEvaluates incoming logs after model training
Logs Insights commandPerforms on-demand anomaly analysis for a query range

Configuration

SettingRecommendation
Training dataA detector uses up to the prior two weeks of events; initial training can take about 15 minutes
ScopeUse log groups with stable application patterns; the feature is not intended as a network/access anomaly detector
VisibilitySet how long detected anomalies remain visible (21 days by default)
Log classRequires the Standard log class
Warning

Anomaly detection requires the Standard log class and works best on log groups with stable application patterns. It is not intended as a network or access anomaly detector — pair it with dedicated security monitoring for those signals.

Cost Optimization

CloudWatch costs scale with volume; right-sizing retention, resolution, and scope keeps observability affordable at scale. For broader AWS cost strategies, see the Cost Optimization Guide.

StrategyDescriptionPotential Savings
Log retentionRight-size retention periodStorage cost
Log class/tieringSelect a lower-cost class/tiering model only when required features remain availableLower ingestion/storage cost depending on the option
Metric consolidationReduce custom metricsPer-metric cost
Dashboard cleanupRemove unused paid dashboards and widgetsLower dashboard/API cost
Alarm optimizationRight-size evaluation periodsEvaluation cost
Canary schedulingReduce frequency or use business-hour schedules only for noncritical journeys; continuously test critical pathsExecution cost
Export to S3Use export tasks for archival, not as a continuous real-time streamCloudWatch storage reduction
Tip

Use S3 export tasks for archival rather than as a continuous real-time stream, and keep canaries running continuously only on critical paths — both are of the highest-impact ways to trim CloudWatch spend without losing coverage.

Additional Best Practices

  • Standardize account/Region, environment, service, and resource dimensions, but avoid unbounded high-cardinality dimensions such as request IDs in custom metrics.
  • Alarm on symptoms that affect users and on imminent capacity exhaustion. Route notifications through an owned, tested escalation path and document the response in alarm descriptions or runbook links.
  • Use cross-account observability or centralized telemetry accounts for multi-account environments; protect centralized log destinations with least-privilege resource policies.
  • Encrypt sensitive logs, apply data-protection policies where useful, and never emit credentials, authorization headers, or unnecessary personal data.
  • Set explicit retention on every log group and query only the required time range/fields to reduce Logs Insights scan cost.
