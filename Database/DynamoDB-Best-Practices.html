DynamoDB Best Practices

DynamoDB is AWS's fully managed, serverless NoSQL database built for single-digit millisecond latency at any scale. Because performance, cost, and reliability hinge on how you model data and configure capacity, getting these decisions right early prevents expensive re-architecture later.

Data Modeling

Choosing the right data modeling pattern determines whether your application gets millisecond responses or suffers from excessive request fan-out and throttling. The patterns below are starting points, not rules; see also Database Integration Patterns for how DynamoDB fits into broader architecture.

Single-Table Design

Co-locate related entity items around explicitly modeled access patterns. Reduces request fan-out and supports transactional/item-collection access; it is not automatically best for every workload.

Normalized Design

Separate tables with references. Best for independent scaling and clear boundaries.

Denormalized Design

Duplicate data to avoid joins. Suited to read-heavy workloads where you want to reduce query complexity.

Aggregate Pattern

A collection of items under one PK, such as a user profile with multiple attributes.

Collection Table Pattern

Multiple entity types in one table, useful for multi-entity application data.

Index Pattern

Duplicate data with different access patterns, enabling multiple query patterns on the same data.

Key Schema Design

Your key schema is the foundation of every query and determines how data is distributed across partitions, directly affecting throughput and latency.

Key TypePurposeConstraintsBest Practice
Partition keyDetermines logical item collection and physical distribution1-2,048 bytesHigh-cardinality, evenly distributed access
Sort keyOrders items within a partition-key value1-1,024 bytesEnables range and begins-with key conditions
Composite KeyHK + RK combinationBoth required for queriesDesign for query patterns first

Partition Key Selection

A poorly chosen partition key creates hot partitions that throttle under load, while a good one distributes traffic evenly without manual intervention.

CharacteristicGood Partition KeyBad Partition Key
CardinalityHigh (many distinct values)Low (few distinct values)
DistributionEven across valuesHot partitions on few values
GrowthUnbounded or slow growthTime-based (date, hour)
ExamplesUserID, OrderID, UUIDStatus, Type, Date

Capacity Modes

Picking the wrong capacity mode means either overpaying for idle reserved capacity or being throttled when you need throughput most.

On-Demand vs Provisioned

FeatureOn-DemandProvisioned
PricingPer read/write request unit actually consumedProvisioned RCU/WCU-hours; requests above available capacity can be throttled rather than billed as "overage"
ScalingAutomatic within table/account quotas and warm-throughput behaviorManual, scheduled, or Application Auto Scaling
BurstNo burst neededBurst from unused capacity
PredictabilityVariable costPredictable cost
Best ForUnpredictable, spiky workloadsSteady, predictable workloads
Cost comparisonOften attractive for new, unpredictable, or spiky trafficOften attractive for steady, forecastable traffic; calculate with actual item sizes, consistency, peaks, headroom, and current Regional rates
Note

On-demand tables instantly support previously reached traffic and up to twice the previous peak. A jump beyond twice the previous peak within 30 minutes can throttle; pre-warm or ramp traffic gradually. Configurable maximum throughput and account/table quotas can also cap traffic.

Auto Scaling

Misconfigured scaling bounds leave you throttled during spikes or bleeding money during quiet periods, so getting the min/max/target right matters.

SettingRecommendationReason
Min CapacityCover the normal trough and known scale-out delayAvoid throttling before Application Auto Scaling reacts
Max CapacityCover tested peak plus operational headroom and account quotasBound cost without blocking legitimate peak traffic
Target UtilizationStart from the console default of 70%, then tune with load testsLower targets provide more burst headroom at higher idle cost
Scheduled scalingPre-scale known peaksTarget tracking is reactive and cannot absorb every abrupt spike
Scaling policyTarget trackingSimple, effective

Global Secondary Indexes (GSIs)

Every GSI adds write amplification and storage cost, so create only the indexes that serve real query patterns rather than hypothetical ones.

Tip

Projection choice is the most cost-effective GSI optimization lever: over-projecting silently inflates storage and write costs for every indexed item. Prefer KEYS_ONLY or INCLUDE unless you truly need all attributes.

GSI Design

ConsiderationRecommendation
Number of GSIsAdd only for defined access patterns; default quota is 20 per table and can be adjustable
Number of LSIsMax 5 per table, must be defined at table creation
Sparse indexesOnly index items that need the query pattern
Projected attributesUse INCLUDE or KEYS_ONLY to reduce cost
Partition keyDifferent from table PK for different access patterns
Sort keyEnable range queries and filtering

Projection Types

TypeDescriptionCost ImpactUse Case
ALLAll attributes projectedHighestNeed all data from index
KEYS_ONLYOnly key attributesLowestGet item key, then fetch full item
INCLUDESpecific non-key attributesMediumNeed specific attributes from index

Performance Optimization

Read Optimization

Read-heavy applications that don't batch or project efficiently burn capacity on network overhead and payload transfer rather than actual data retrieval.

TechniqueDescriptionImpact
BatchGetItemFetch up to 100 items or 16 MB per callReduce network round trips; retry UnprocessedKeys with exponential backoff
Parallel requestsMultiple concurrent GetsHigher aggregate throughput
DAX (DynamoDB Accelerator)Write-through and item/query caches for compatible eventually consistent readsMicrosecond cache hits; validate operation, consistency, and Region support
ProjectionExpressionReturn only needed attributesCan reduce response payload, but does not reduce read capacity consumed because billing uses item size before projection
Consistent readsOnly when necessaryEventually consistent is cheaper/faster

Write Optimization

Write patterns that ignore batching, atomicity needs, or item-size semantics waste capacity units and create unnecessary retry loops under load.

TechniqueDescriptionImpact
BatchWriteItemPut/delete up to 25 items per callReduce round trips; it is not transactional and callers must retry UnprocessedItems
TransactWriteItemsAtomic multi-item writesConsistency across items
Parallel writesDifferent partition keysHigher aggregate throughput
Time-to-Live (TTL)Auto-expire itemsReduce storage cost
PutItem vs UpdateItemChoose for semantics and conditional-write needsUpdateItem does not inherently save WCUs: write capacity is based on the larger item size before or after the update

Hot Partition Avoidance

Warning

Hot partitions are the most common cause of throttling in production, and they cannot be fixed by simply increasing provisioned capacity. Redesign the key or write model instead.

SymptomCauseSolution
ProvisionedThroughputExceededExceptionSingle partition overloadRedesign partition key
High latency/throttling for one item collectionSkewed partition-key accessWrite-shard the partition key where the access pattern can query/aggregate shards; a sort-key suffix alone does not distribute writes
Uneven capacity usageSkewed data distributionUse UUID, hash prefix
Write throttling on a specific itemHot item updatesUse sharded counters, aggregation, buffering, or a different write model; UpdateItem alone does not remove a hot key

DAX (DynamoDB Accelerator)

DAX Features

Understanding DAX's caching semantics is essential because write coherence behavior differs depending on whether writes go through DAX or directly to DynamoDB.

FeatureDescription
In-memory cachingSub-millisecond read latency
Cache coherenceWrites made through DAX update its item cache; writes made directly to DynamoDB can remain cached until TTL expiry
Cluster modeMulti-node for high availability
Supported operationsCacheable reads: GetItem, BatchGetItem, Query, and Scan. DAX also supports documented write-through and transactional APIs, but passes strongly consistent and transactional reads through to DynamoDB
TTLConfigurable per-item cache duration

DAX Sizing

Under-provisioned DAX clusters become a bottleneck themselves, while over-provisioned ones add cost without improving cache hit rates.

Node TypeRelative CapacityUse Case
dax.r6g.largeBaselineSmall workloads
dax.r6g.xlarge~2x largeMedium workloads
dax.r6g.2xlarge~4x largeLarge workloads
dax.r6g.4xlarge~8x largeVery large workloads
Note

Memory per node type scales with the underlying R6g instance size; check current values on the DynamoDB pricing page before sizing. A DAX cluster supports 1 primary + up to 10 read replicas (max 11 nodes); use at least 3 nodes across different AZs for production fault tolerance.

Access Control

Without fine-grained IAM policies and VPC endpoints, DynamoDB tables are accessible to any IAM principal with broad permissions, creating a compliance and security risk.

MethodDescription
IAM PoliciesFine-grained table, index, and attribute-level access
Resource-level permissionsSpecific table and GSI ARNs
Condition keysdynamodb:Attributes, dynamodb:LeadingKeys, dynamodb:Select, and other documented keys
VPC endpointsUse a DynamoDB gateway endpoint for private routing from a VPC; apply endpoint and IAM policies together

IAM Policy Conditions

Condition keys let you enforce tenant isolation and attribute-level access control without creating separate tables or application-level checks.

Condition KeyDescription
dynamodb:AttributesRestrict attributes that a request can access; pair with dynamodb:Select as documented
dynamodb:LeadingKeysRestrict partition-key values for fine-grained access
dynamodb:SelectRestrict result-selection behavior
dynamodb:ReturnConsumedCapacityControl whether callers request consumed-capacity details

Streams & Triggers

Stream View Types

The stream view type determines how much data downstream consumers receive, directly impacting Lambda invocation cost and processing latency.

KEYS_ONLY

Only key attributes. Minimal data; a key lookup is needed for the full item.

NEW_IMAGE

Entire item after update. Best for processing updated state.

OLD_IMAGE

Entire item before update. Useful for audit and rollback.

NEW_AND_OLD_IMAGES

Both before and after images. Needed for change detection and diffs.

Lambda Triggers

Lambda trigger misconfiguration is a common source of lost stream records and cascading failures when downstream processing falls behind (see Lambda Best Practices for consumer-side tuning).

SettingRecommendation
Batch sizeMatch to processing capacity
ParallelizationEnable for faster processing
RetryConfigure retry on failure
DestinationSend failures to SQS/S3
Tumbling windowBatch records by time window

Table Classes

Choosing the wrong table class means paying a premium for throughput you don't need or storage you don't use, so match the class to your access pattern.

Table ClassStorage CostThroughput CostBest For
DynamoDB StandardHigherLowerDefault; most workloads
DynamoDB Standard-IALowerHigherStorage-dominant, infrequently accessed tables; evaluate current price ratios by Region

Cost Components

Model table and GSI read/write units, table-class storage, backup/PITR storage, Streams reads, change-data capture, exports/imports, global-table replicated writes and replica storage, DAX, and applicable data transfer. Prices and free-tier treatment vary; confirm the deployment Region on the DynamoDB pricing page.

Global Tables

Multi-Region Replication

Global tables introduce consistency trade-offs and cross-region write costs that must be understood before committing to a multi-active architecture.

FeatureDescription
Active-ActiveRead/write in all regions
Consistency modesMulti-Region eventual consistency (MREC, default) or multi-Region strong consistency (MRSC, selected at creation and subject to topology/feature constraints)
Conflict resolutionMREC and multi-account global tables use asynchronous replication with last-writer-wins; MRSC provides strongly consistent multi-Region operations
Replication latencyMonitor ReplicationLatency; do not encode a sub-second assumption into correctness or RPO calculations
Capacity configurationBilling mode and replica/index configuration are coordinated as a global table; provisioned auto scaling is managed across replicas rather than as unrelated tables

Global Table Considerations

Cross-region write conflicts and replication lag can cause data inconsistency if the application isn't designed to handle eventual consistency semantics.

ConsiderationRecommendation
Write conflictsDesign to minimize cross-region writes to same item
ConsistencyMREC cross-Region replication is eventual; use MRSC only when its stronger semantics and topology constraints fit the workload
CostData replicated to all regions
TTLMREC TTL settings synchronize across replicas; MRSC global tables do not support TTL
StreamsDynamoDB Streams can be enabled on global-table replicas; consumers must handle replicated changes and possible duplicate processing
