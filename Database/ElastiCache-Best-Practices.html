Engine Selection

Engine naming note

Amazon ElastiCache supports Valkey, Redis OSS, and Memcached. AWS recommends evaluating the newest supported engine release; current ElastiCache documentation includes Valkey 9.x while Redis OSS support ends at 7.1. Valkey is the normal default for new Redis-compatible workloads, but verify client and feature compatibility before migration.

Valkey / Redis OSS vs Memcached

The engine choice locks in the data structures, durability options, and HA capabilities available to your workload. Picking the wrong engine means either paying for unused features or discovering missing capabilities after deployment.

High AvailabilityMulti-AZ with automatic failoverNo built-in HA

Serverless optionYes (ElastiCache Serverless)Yes (ElastiCache Serverless)
Pub/SubYesNo

Valkey / Redis OSS Architecture

Deployment Modes

Your deployment mode dictates how data is partitioned, how failover behaves, and how much operational overhead you carry. Choosing incorrectly can block scaling or leave you without HA when a failure occurs.

ModeDescriptionUse Case
Cluster Mode DisabledSingle shard, primary + up to 5 replicas, Multi-AZSimplicity, HA, smaller datasets
Cluster Mode EnabledSharded, auto-reshardingLarge datasets, high throughput

Cluster Mode

Cluster mode enables horizontal scaling through sharding but introduces key design constraints like cross-slot restrictions and hash-tag requirements. Understanding these tradeoffs before enabling cluster mode avoids painful application refactoring later.

FeatureDescription
Shards (Nodes Groups)Independent partitions of data
Online reshardingAdd/remove shards while serving traffic on supported versions; test latency and capacity impact
Cross-slot operationsNot supported (design keys carefully)
Hash tagsForce related keys to same slot
Node/shard quotaDefault: 90 nodes per cluster-mode-enabled cluster. An approved increase can allow up to 500 total nodes or 500 shards (with no replicas) on supported Valkey/Redis OSS versions; replicas reduce the possible shard count

Multi-AZ Configuration

Multi-AZ with auto-failover is the difference between a cache outage lasting minutes versus hours when an AZ fails. Skipping replicas for cost savings trades a small recurring cost for potentially catastrophic downtime.

SettingDescriptionRecommendation
Auto-failoverPromote a replica after primary failureEnable for production workloads that require HA; cluster mode enabled requires it
Number of replicas1-5 per shardMinimum 1 for HA
Availability zonesAutomatic placementSpread across AZs
Preferred maintenance windowPatching windowLow-traffic period

Backup & Durability

A cache is not a system of record

ElastiCache is primarily a cache, not a system of record. Node-based Valkey/Redis OSS supports managed snapshots and restore into a new cache. Replication and Multi-AZ reduce downtime but do not by themselves provide a zero-data-loss guarantee. Do not describe ElastiCache as offering user-managed RDB+AOF durability: persistence controls and availability depend on the ElastiCache engine/version, and serverless parameters are service-managed.

Defining your durability requirements before deployment determines whether ElastiCache alone is sufficient or whether you need a complementary durable store such as RDS or DynamoDB. Assuming the cache is your source of truth without testing restore paths is a common cause of data loss.

RequirementGuidance
Rebuildable cacheTreat the source database/object store as authoritative; test cache warm-up and stampede protection
Sessions or other stateDefine acceptable RPO, enable supported backups/replication, and test failover plus restore. Consider a durable database if losing acknowledged writes is unacceptable
Zero-data-loss failoverEvaluate the documented Multi-AZ transactional-log durability available in supported newer Valkey versions, including its Region/version and Global Datastore constraints
Cross-Region recoveryGlobal Datastore replication is asynchronous; monitor lag and run planned/unplanned failover exercises

Security

Security Checklist

An unsecured cache is an open door to your data layer—without encryption, VPC isolation, and access controls, a compromised cache credential can expose your entire dataset. These controls follow the principle of defense in depth so that no single failure exposes data.

Dangerous Commands to Disable

A single accidental or malicious dangerous command can wipe an entire cache or halt the engine, turning a recoverable situation into a full outage. Disabling these commands at the ACL and parameter-group level is a low-effort control that prevents catastrophic human error.

CommandRiskAction
FLUSHDBDelete all keys in databaseDeny with RBAC ACLs and, for supported node-based versions, block/rename in a custom parameter group
FLUSHALLDelete all keys in all databasesDeny with RBAC ACLs and, for supported node-based versions, block/rename in a custom parameter group
KEYSCan block the engine over a large keyspaceDeny for application users; use cursor-based SCAN where appropriate
DEBUGAdministrative/debug operationsDeny for application users
CONFIGRuntime configuration accessDeny for application users; manage supported settings through ElastiCache parameter groups

Cache Hit Rate Analysis

There is no service-wide "good" cache-hit ratio. Establish a target from source-load reduction, end-to-end latency, object popularity, negative caching, and freshness requirements. Segment hits/misses by operation and key family; a high ratio can still hide a hot miss path or stale-data problem.

Data Consistency Patterns

Choosing a consistency pattern is one of the most consequential cache design decisions; for broader coverage of caching strategies, see Caching & Content Delivery Patterns.

Cache-Aside Pattern

The cache-aside pattern is the simplest approach but introduces a cold-start penalty on every miss. Understanding this tradeoff helps you decide whether TTL tuning, pre-warming, or a different pattern is needed for latency-sensitive paths.

StepActionDescription
1Check cacheGET key from ElastiCache
2Cache hitReturn cached value
3Cache missQuery database
4Populate cacheSET key with DB value + TTL
5Return valueReturn to application

Write-Through Pattern

Write-through trades write latency for stronger consistency, which matters when stale cache data causes business logic errors. The ordering of source commit versus cache update is the single most important detail to get right.

StepActionDescription
1Write source of truthCommit the durable database write
2Update or invalidate cacheApply a versioned/idempotent cache update only after the durable commit, or use a transactional outbox/change stream
3Return resultDefine failure handling so cache and source cannot silently diverge

Pattern Comparison

Choosing the wrong consistency pattern creates subtle bugs that surface only under high concurrency or during failover. This comparison helps you match the pattern to your tolerance for stale data versus write latency.

PatternRead PerformanceWrite PerformanceConsistencyComplexity
Cache-AsideGood (after first miss)GoodEventualLow
Write-ThroughExcellentSlower writesStrongerMedium
Write-BehindExcellentFast writesEventualHigh
Read-ThroughExcellentGoodMediumMedium

Global Datastore & Serverless

Multi-Region replication and serverless deployment address two fundamentally different problems: disaster recovery versus operational simplicity. Understanding which capability solves your actual constraint prevents over-engineering or under-protecting your cache.

FeatureDescription
Global DatastoreAsynchronous cross-Region replication for supported node-based Valkey/Redis OSS clusters. It supports one primary and up to two secondary Regions, requires the same account, and does not make RPO zero; test failover and monitor lag
ElastiCache ServerlessAutomatically scales compute and data storage for Valkey, Redis OSS, or Memcached; uses TLS and engine-specific serverless limits/settings, so verify client compatibility and quotas
