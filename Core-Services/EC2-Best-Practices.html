EC2 Best Practices

EC2 provides the foundational compute layer for virtually every AWS workload, making its configuration a primary driver of cost, performance, and security across the entire account. Misconfigured instances are among the most common sources of cloud waste and vulnerability, so establishing disciplined practices here yields outsized returns.

Graviton and Nitro

Leveraging Graviton and Nitro infrastructure unlocks significant cost and performance gains while reducing the software overhead that traditionally consumes instance resources.

TopicGuidance
AWS Graviton (arm64)Prefer Graviton-based instances (e.g., m7g, c7g, r7g, t4g) for supported workloads — typically better price-performance than equivalent x86 instances; requires arm64-compatible AMIs/binaries
AWS Nitro SystemMany current-generation instance families use the Nitro System. Verify the selected instance type; Nitro offloads networking, storage, management, and security functions to dedicated hardware and a lightweight hypervisor
Nitro EnclavesUse for isolated, attestable compute environments to process highly sensitive data (e.g., PII, keys)

Right-sizing guidelines

A systematic right-sizing process prevents the common trap of over-provisioning "just to be safe."

Warning

Over-provisioning can quietly inflate monthly bills by 30–40%. Review actual utilization before committing to a larger instance type.

StepActionTool
1Review a representative period that includes peaks and business cyclesCloudWatch metrics and application telemetry
2Review over- and under-provisioning recommendationsAWS Compute Optimizer
3Validate CPU, memory, network, EBS, latency, and queue-depth constraints against workload SLOsCloudWatch alarms and load tests
4Test candidate instance types in non-production and model costAWS Pricing Calculator
5Migrate using AMI copy or stop/start with new typeAWS Console / CLI

Security hardening

IMDS (Instance Metadata Service)

The instance metadata service is a frequent attack vector for credential theft, so hardening IMDS access is one of the highest-impact security controls for any EC2 deployment.

Note

Require session-oriented IMDSv2 as defense in depth against several metadata-access attack paths. A hop limit of 1 can break container access — use the smallest value that supports the workload and block metadata access for containers that do not need it.

SettingValueDescription
IMDS Versionv2 onlyRequire session-oriented IMDSv2 as defense in depth against several metadata-access attack paths
Hop Limit1 for direct host access; commonly 2 for containersA limit of 1 can break container access. Use the smallest value that supports the workload and block metadata access for containers that do not need it
Token RequirementRequiredIMDSv2 requires session token

Security group rules

Security groups function as a stateful firewall at the instance level, and overly permissive rules are the leading cause of unauthorized EC2 exposure in production environments. For subnet- and route-level controls, see VPC best practices.

Warning

Overly permissive security group rules are the leading cause of unauthorized EC2 exposure in production. Keep ingress least-privilege and avoid 0.0.0.0/0 on any port except public HTTPS.

Auto Scaling

Launch configuration vs launch template

Using launch templates instead of legacy launch configurations unlocks versioning, default selection, and compatibility with modern Auto Scaling features that launch configurations no longer support.

Warning

Launch configurations are legacy. Accounts created on or after October 1, 2024 cannot create them — migrate existing Auto Scaling groups to launch templates.

FeatureLaunch configurationLaunch template
VersioningNoYes
Default selectionNoYes
Current availabilityAccounts created on or after October 1, 2024 cannot create launch configurationsSupported for current Auto Scaling features
RecommendationLegacy; migrate existing Auto Scaling groupsUse launch templates for new and updated workloads

Lifecycle management

Instance state management

Understanding the data persistence implications of each action prevents accidental data loss and ensures the right recovery strategy is applied for each scenario.

Warning

Stop/start, hibernate, and terminate all lose instance store (ephemeral) data. Only EBS-backed data survives stop/start; hibernation additionally requires an encrypted EBS root volume large enough for RAM.

ActionWhen to useConsiderations
Stop/StartMaintenance, cost savingData on EBS preserved; instance store (ephemeral) data is LOST
HibernatePreserve RAM state and resume processesMust be enabled at launch; requires a supported AMI/type and an encrypted EBS root volume large enough for RAM. Instance-store data is lost
TerminatePermanent removalAll ephemeral data lost
RebootApplication recoveryFaster than stop/start
