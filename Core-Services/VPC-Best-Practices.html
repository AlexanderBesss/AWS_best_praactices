VPC Best Practices

A VPC gives you an isolated, logically separated section of AWS where you control networking, IP addressing, and security boundaries. Proper VPC design is the foundation for secure, scalable, and cost-effective cloud infrastructure — everything else builds on top of it.

Network architecture

Recommended VPC design

A well-structured VPC layout separates traffic by trust level and function, making it easier to apply security controls and scale individual tiers independently. For database-tier workloads, see RDS Best Practices.

ComponentRecommendationCIDR Example
VPC CIDRSize from forecast address demand, service scaling behavior, hybrid connectivity, and non-overlap requirements; use VPC IPAM for organizational allocation10.0.0.0/16 is an example, not a universal default
Public SubnetsOne per used AZ where internet-facing load balancers or NAT gateways require themExample: 10.0.1.0/24, 10.0.2.0/24
Private application subnetsAt least two AZs for workloads with an HA requirement; leave growth headroomExample: 10.0.10.0/24, 10.0.11.0/24
Isolated data subnetsNo default route to an internet gateway; size for database ENIs, failover, and growthExample: 10.0.20.0/24, 10.0.21.0/24
IPv6Plan dual-stack or IPv6-only subnets where supported to reduce IPv4 pressureVPC IPv6 CIDRs and /64 subnets are common AWS-assigned patterns

Subnet sizing

Sizing subnets correctly prevents running out of IP addresses mid-deployment while avoiding wasted address space that restricts how many subnets you can create.

CIDRUsable HostsUse Case
/2811Smallest supported IPv4 subnet; use only after accounting for service ENIs, scaling, and failover
/2727Small deployments
/2659Medium deployments
/25123Large deployments
/24251Common example, not a universal default
/23507High-density deployments
/221019Very large deployments
Note

AWS reserves 5 IPs in each subnet (network address, VPC router, DNS, future use, and broadcast address), and /28 is the smallest subnet AWS allows.

AWS Transit Gateway

Transit Gateway eliminates the N-squared routing complexity of peering meshes, making it essential when you manage more than a handful of VPCs or need hybrid connectivity.

Security groups

Best practices

Security groups are the first line of defense at the instance level; misconfigurations here are among the most common causes of cloud security incidents.

PracticeDescription
Use SG referencesReference other SGs instead of IP ranges
Understand defaultsA new custom security group has no inbound rules and an allow-all outbound rule. The VPC default security group also allows inbound traffic from itself
Named SGsUse descriptive names (e.g., web-allow-https)
Minimal rulesFewest rules necessary
Audit regularlyReview and remove unused rules
SG modifications take effect immediatelyNo instance restart required for rule changes

Common SG configurations

Layered SG rules that reference each other create a chain of trust, so a compromise in one tier doesn't automatically grant access to the next. For load balancer-specific guidance see Load Balancing Best Practices.

ResourceInbound RulesOutbound Rules
Web Server (ALB)TCP/443 from 0.0.0.0/0, TCP/80 from 0.0.0.0/0All to private app SG
Application ServerTCP/8080 from ALB SGTCP/5432 to DB SG; TCP/443 to explicitly required destinations (routes separately determine the network path)
DatabaseTCP/5432 from app SG onlyRestrict only if the engine/agents do not require broader egress; security groups do not target an internet gateway
Bastion HostTCP/22 from corporate IP onlyAll to private subnets
Batch WorkerNone (or from coordinator SG)TCP/443 to S3 VPC endpoint

AWS Network Firewall & Gateway Load Balancer

Centralized traffic inspection catches threats that security groups and NACLs can't — like encrypted payload inspection, domain filtering, and signature-based intrusion detection.

ComponentPurposePlacement
AWS Network FirewallStateful, managed IDS/IPS and traffic filtering (domain, protocol, signature-based rules)Dedicated inspection subnet/VPC, typically routed via Transit Gateway
Gateway Load Balancer (GWLB)Transparently insert third-party virtual appliances (firewalls, IDS/IPS) inlineCentralized inspection VPC, paired with GWLB endpoints in spoke VPCs
Centralized Inspection ArchitectureRoute inter-VPC/internet traffic through a shared inspection VPCCombine with Transit Gateway for hub-and-spoke traffic inspection

Network ACLs

NACL vs security group

NACLs and security groups operate at different layers; knowing the distinction prevents subtle rule conflicts and the "why is my traffic blocked" debugging cycle.

FeatureSecurity GroupNetwork ACL
LevelInstance levelSubnet level
StatefulYes (return traffic auto-allowed)No (explicit rules needed)
RulesAllow onlyAllow and Deny
ScopeSpecific instancesAll instances in subnet
Rule NumbersNo orderingOrdered by rule number
DefaultsCustom SG: no inbound, allow-all outbound; default SG also allows inbound from itselfDefault NACL allows all; a new custom NACL denies all until rules are added

NACL rule design

Because NACLs are stateless, every direction and ephemeral port range must be explicitly accounted for — or legitimate return traffic will be silently dropped.

Rule #TypeProtocolPortActionPurpose
100HTTPSTCP443AllowInbound HTTPS
200HTTPTCP80AllowInbound HTTP
300EphemeralTCP1024-65535AllowReturn traffic
*All TrafficAllAllDenyImplicit final rule; cannot be removed
Note

NACLs are stateless, so define corresponding outbound rules and the client/server ephemeral-port ranges actually used by the operating systems and load balancers. The sample above is illustrative, not a complete production rule set.

VPC endpoints

Endpoint types

Endpoints keep traffic to AWS services off the public internet, reducing exposure, eliminating NAT costs, and satisfying compliance requirements that mandate private connectivity.

Tip

Prefer free gateway endpoints for S3 and DynamoDB; reserve interface endpoints for services that only offer them. Each interface endpoint ENI consumes a subnet IP, so place them deliberately.

ServiceEndpoint TypeCostUse Case
S3GatewayFreePrivate S3 access
DynamoDBGatewayFreePrivate DynamoDB access
LambdaInterface$ per hour + dataPrivate Lambda invocation
SNS/SQSInterface$ per hour + dataPrivate messaging
Secrets ManagerInterface$ per hour + dataPrivate secret retrieval
KMSInterface$ per hour + dataPrivate key operations

Endpoint best practices

Proper endpoint placement and policy restrictions ensure private connectivity actually delivers the security and performance benefits it promises.

PracticeDescription
Use Gateway endpoints for S3/DynamoDBFree, high performance
Deploy interface endpoints in required AZsUse one endpoint ENI per required AZ and enable private DNS where supported; gateway endpoints are route-table targets rather than per-AZ ENIs
Restrict with policiesLimit accessible resources

Monitor with CloudWatchTrack endpoint metrics

Flow logs

Flow log configuration

Flow logs are your only network-level visibility into what traffic is actually flowing through your VPC, making them essential for troubleshooting, compliance, and threat detection.

SettingRecommendationReason
Log LevelACCEPT and REJECTFull visibility
DestinationS3 or CloudWatch LogsStorage and analysis
Traffic TypeALLCapture all traffic
Max Aggregation IntervalChoose 1 or 10 minutes where supportedMatch detection latency, volume, and cost requirements; actual aggregation can be shorter under some conditions
Destination encryptionConfigure CloudWatch Logs or S3 encryption and least-privilege delivery permissionsFlow Logs has no standalone "TLS encryption" toggle

Flow log analysis

Raw flow logs are voluminous and hard to interpret at scale; pairing them with the right analysis tools turns noise into actionable security and performance insights. See CloudWatch Best Practices for log retention and alerting patterns.

CIDR planning

Private IP ranges (RFC 1918)

Picking the right RFC 1918 range upfront determines how much address space you have for growth and whether you'll run into conflicts with on-premises networks or other VPCs.

RangeCIDRTotal IPv4 Addresses
10.0.0.0 - 10.255.255.255/816,777,216
172.16.0.0 - 172.31.255.255/121,048,576
192.168.0.0 - 192.168.255.255/1665,536

Overlap avoidance

CIDR overlaps silently break connectivity at peering, Transit Gateway, and Direct Connect boundaries — detecting and preventing them early saves weeks of network debugging.

ScenarioRiskSolution
VPC peering with overlapping CIDRsNot allowedUse different CIDR ranges
Direct Connect with on-prem overlapRoute conflictsRenumber the overlapping network or design an explicit NAT/address-translation architecture; Transit Gateway does not resolve overlapping CIDRs
Multiple accounts in OrganizationPlanning complexityCentralized IPAM
