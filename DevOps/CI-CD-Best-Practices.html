CI/CD Best Practices

CI/CD is the backbone of modern software delivery, enabling teams to ship changes quickly, safely, and reproducibly. Automating the build, test, and deployment pipeline reduces manual errors, accelerates feedback loops, and ensures every change is validated before reaching production.

Pipeline architecture

CodePipeline stages

A well-structured pipeline stages code from source to production, ensuring each step has a clear responsibility and ownership.

StageActionDescription
SourceCodeCommit, S3, ECR, or CodeConnections for GitHub/GitLab/BitbucketSource revision or image
BuildCodeBuildCompile, test, package
TestCodeBuild, AWS Device Farm, third-party toolsAutomated testing
DeployCodeDeploy, ECS, CloudFormation, Elastic Beanstalk, S3, or third-party deploy actionsApplication/infrastructure deployment
ApproveManual approvalHuman gate before production

Pipeline strategy

A tiered pipeline strategy balances speed and safety by automating lower environments while gating production with human approval.

EnvironmentPipelinePromotion
DevelopmentAutomatic on commitEvery commit
StagingAutomatic from devAfter dev success
ProductionManual approvalAfter staging success
Note

A manual approval is an authorization gate, not a substitute for automated tests. Add deployment timeouts, rollback criteria, and post-deployment verification as code.

Blue/green deployment

Blue/green deployments eliminate downtime by running two identical environments and switching traffic only after validation.

PhaseActionDescription
1Create green environmentNew deployment
2Run tests on greenValidate deployment
3Shift trafficGradual or full switch
4Monitor greenVerify stability
5Terminate blueClean up old environment
6Swap on failureQuick rollback

Canary deployment

Canary deployments limit blast radius by gradually exposing a small subset of traffic to the new version before a full rollout.

SettingRecommendation
PercentageChoose from a predefined or custom CodeDeploy configuration based on acceptable blast radius
IntervalLong enough to observe representative traffic and alarm evaluation periods
Failure thresholdConfigure deployment-group CloudWatch alarms and automatic rollback
MetricsCloudWatch alarms for rollback criteria
DurationMatch traffic volume and the time needed to detect regressions

GitOps deployments

GitOps tools keep cluster state in sync with a Git repository, providing an auditable, declarative deployment model.

ToolTargetDescription
Argo CDEKSDeclarative, Git-sourced continuous delivery for Kubernetes
FluxEKSGitOps toolkit reconciling cluster state from Git
CodePipeline + CodeDeployECS, Lambda, EC2AWS-native push-based CD (non-GitOps)

Use GitOps for Kubernetes workloads where the Git repository is the single source of truth and an in-cluster controller reconciles drift; use CodePipeline/CodeDeploy for AWS-native push-based deployments to ECS, Lambda, or EC2. For cluster-level concerns, see ECS/EKS Best Practices.

Security

Pipeline security

Securing the pipeline itself prevents it from becoming the weakest link in the deployment chain. Pipeline roles should follow the least-privilege principles covered in IAM Best Practices.

ControlImplementation
Secrets managementSecrets Manager or Parameter Store secret references; never plaintext pipeline/build environment variables
IAM rolesLeast privilege for pipeline roles
Scan for vulnerabilitiesDependency/SAST tooling in the build; Amazon Inspector for supported ECR images and deployed compute
Container scanningPush immutable images to ECR, evaluate scan findings, and promote by digest
Infrastructure scanningCheckov, cfn-nag for IaC
Approval gatesManual approval for production
Audit trailCloudTrail for pipeline actions
Warning

Never store plaintext secrets in pipeline or build environment variables. Use Secrets Manager or Parameter Store secret references so credentials never leak into logs, source code, or build artifacts.

Additional best practices

  • Use separate artifact, deployment, and administration roles; restrict iam:PassRole to the exact service roles each pipeline needs.
  • Encrypt artifact stores, block public access, enable versioning where rollback depends on prior artifacts, and apply lifecycle policies.
  • Prefer short-lived identity federation for external CI systems and pin third-party actions and dependencies.
Tip

Make artifacts immutable and promote the same tested artifact between environments instead of rebuilding it. This guarantees that what was validated in staging is exactly what runs in production.
