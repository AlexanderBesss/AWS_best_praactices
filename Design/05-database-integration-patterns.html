Database Integration Patterns

How to connect Lambda, SNS, and SQS with AWS database services without exhausting connections, losing events, or paying for latency you did not ask for. Seven production patterns, each with its trade-offs spelled out.

Patterns at a glance

Seven patterns cover the common shapes of serverless-to-database integration. Pick by workload, not by default.

Lambda + DynamoDB direct

The simplest and most performant NoSQL path: no connection pool to manage, but every query shape must be designed up front.

Lambda + RDS via RDS Proxy

Bursty or high-concurrency access to relational databases that would otherwise exhaust max_connections.

DynamoDB trigger pipeline

Fan item changes out to search indexes, caches, and archives without touching every write path.

CQRS with event sourcing

Complex domains where reads and writes diverge and a full audit trail of state changes is required.

Multi-Region architecture

Global low-latency reads and disaster recovery with defined RPO/RTO targets.

Connection management for Lambda

Budget concurrency, reuse connections, and bound pools to avoid connection exhaustion under scale-out.

SQS + transactional outbox

Atomic business-data persistence plus reliable at-least-once event publication from a database transaction.

Pattern 1: Lambda + DynamoDB direct integration

The simplest and most performant integration for NoSQL workloads.

Why this pattern?

DynamoDB's HTTPS API does not require a persistent database session, so there is no database connection pool to exhaust or relational login handshake for each new Lambda execution environment. SDK clients should still be initialized outside the handler so their HTTP connections can be reused; DNS, TLS, signing, and network latency still exist. A concurrency burst is instead constrained by Lambda concurrency, DynamoDB throughput/quotas, hot partitions, and downstream capacity. DynamoDB Streams also provides a managed item-change feed without table polling. Pair this with DynamoDB Best Practices for key design and capacity guidance.

Trade-off

You give up SQL joins, ad hoc query flexibility, and multi-table transactions with arbitrary predicates — every access pattern has to be designed up front around partition/sort keys and GSIs, and retrofitting a new query shape later often means a table redesign or a costly Scan. If the workload needs relational integrity, complex reporting queries, or schema flexibility for evolving query patterns, this pattern forces expensive rework rather than a config change.

DynamoDB Stream handler example

dynamodb = boto3.resource('dynamodb')

def lambda_handler(event, context):
    for record in event['Records']:
        event_name = record['eventName']  # INSERT, MODIFY, REMOVE
        old_image = record.get('dynamodb', {}).get('OldImage')
        new_image = record.get('dynamodb', {}).get('NewImage')

        if event_name == 'INSERT':
            process_new_item(new_image)
        elif event_name == 'MODIFY':
            process_update(old_image, new_image)

Pattern 2: Lambda + RDS via RDS Proxy

RDS Proxy is a managed pooling option for bursty or high-concurrency Lambda-to-RDS access; it is not required for every workload.

Tip

Start without a proxy. Reach for RDS Proxy when measured concurrency and connection demand exceed the safe database budget (see Pattern 6). For direct-connection guidance, see RDS Best Practices.

Why this pattern?

Relational databases have a finite, engine- and instance-dependent connection budget, while Lambda can create many concurrent execution environments — each potentially opening a connection. A traffic spike can therefore exceed max_connections and affect every database client. RDS Proxy maintains a bounded backend pool and can multiplex client connections when session state does not pin them. It reduces connection churn and protects database headroom, but it does not remove the database's query, CPU, memory, or connection limits.

Trade-off

The proxy is an additional managed component billed from the capacity of the associated database instances or clusters, and adds a network hop. It also doesn't eliminate query tuning or database capacity limits — a saturated proxy pool queues or times out connection borrows, so pool percentages and borrow timeouts must be sized against measured peak concurrency.

The default RDS Proxy endpoint is read/write and connects to the writer. For Aurora, create a separate read-only proxy endpoint to route connections to available readers; the proxy does not inspect each SQL statement and automatically split reads from writes through one connection.

Lambda + RDS Proxy example

import json
import os
import boto3
import pg8000

# Reuse connection across invocations (outside handler)
db_pool = None
secrets = boto3.client('secretsmanager')

def get_connection():
    global db_pool
    if db_pool is None:
        credentials = json.loads(secrets.get_secret_value(
            SecretId=os.environ['DB_SECRET_ARN']
        )['SecretString'])
        db_pool = pg8000.dbapi.connect(
            host=os.environ['RDS_PROXY_ENDPOINT'],
            port=5432,
            database=os.environ['DB_NAME'],
            user=credentials['username'],
            password=credentials['password'],
            ssl_context=True,
        )
    return db_pool

def lambda_handler(event, context):
    conn = get_connection()
    with conn.cursor() as cur:
        cur.execute("SELECT * FROM orders WHERE id = %s", [event['orderId']])
        return {'order': cur.fetchone()}

Lambda connection reuse

Whether connecting directly or through RDS Proxy, initialize clients outside the handler and validate/reconnect stale connections. Execution-environment reuse is opportunistic, so this reduces connection churn but is not a substitute for a concurrency and connection-budget calculation.

Pattern 3: DynamoDB trigger pipeline

Using DynamoDB Streams to drive event-driven processing pipelines.

Why this pattern?

Without a change feed, keeping downstream systems (search indexes, caches, archives) in sync with a DynamoDB table means every write path has to remember to also update every consumer, or the application has to poll the table for changes. DynamoDB Streams captures item-level mutations in sequence within each item and lets a Lambda event source mapping process shard batches.

Idempotency required

Event source mappings are at-least-once, so duplicate processing can occur; cache invalidation, search indexing, and archival handlers must be idempotent.

Trade-off

Stream records expire after 24 hours, so a consumer that cannot catch up within the retention window needs another recovery source, such as an event store, outbox/archive, export, or table rebuild. The stream and any SNS/SQS fan-out are asynchronous and provide no fixed end-to-end latency guarantee, so this pattern is unsuitable when a downstream read must be immediately consistent with the write.

EventBridge Pipes alternative

EventBridge Pipes can route DynamoDB Streams directly to supported targets such as SQS, SNS, Lambda, or an EventBridge API Destination without a routing Lambda. Use an API Destination for an HTTP endpoint. See EventBridge Best Practices for destination configuration.

When to use DynamoDB Streams

  • Use when you need asynchronous, near-real-time reactions to data changes
  • Use for audit trails, cache invalidation, search indexing
  • Don't use for high-throughput ordered streaming — consider Kinesis Data Streams

Pattern 4: CQRS with DynamoDB + event sourcing

Command Query Responsibility Segregation for complex domains.

Why this pattern?

A single DynamoDB table optimized for writes forces reads to either scan/filter inefficiently or bolt on GSIs that don't match every query shape the application eventually needs, and neither approach preserves a full history of how an item reached its current state — once a write overwrites an attribute, the prior value is gone unless captured separately. CQRS with event sourcing solves both problems by treating the events table as the append-only system of record and letting a stream processor build separate, purpose-built read models for each query pattern; the write path never has to be redesigned to serve a new report or view, and the event log itself is the audit trail.

Trade-off

The read models are only eventually consistent with the command side — a client that writes and immediately reads its own write may see stale data until the stream processor catches up — and the system now has two data stores to keep schema-compatible and operationally healthy instead of one. Rebuilding a read model after a bug fix means replaying the entire event history, which for a large Events table is a non-trivial batch job, not a quick migration.

When to use CQRS with event sourcing

  • Use when you need full audit trail of all state changes
  • Use when read and write access patterns differ significantly
  • Use for complex domains with multiple read views
  • Don't use for simple CRUD — direct database access is simpler

Pattern 5: Multi-Region database architecture

For global applications requiring low-latency reads and disaster recovery.

Why this pattern?

A single-region database ties every user's latency to the distance from that region, and a regional outage takes the entire application down with no failover path — for a global user base or an availability SLA that requires surviving a region-level event, that's a single point of failure the business can't accept. Distributing data across regions (via DynamoDB Global Tables' multi-master replication or Aurora Global Database's fast cross-region replicas) lets reads happen close to the user and gives the application a standby region to fail over to, turning a regional AWS event into a bounded RPO/RTO incident instead of a full outage.

Trade-off

Aurora Global Database has one writer Region; write forwarding from a secondary still executes the write in the primary, and failover changes the primary. DynamoDB global tables offer multi-Region eventual consistency (MREC, the default) and multi-Region strong consistency (MRSC). MREC can expose stale cross-Region reads and resolves concurrent same-item writes with last-writer-wins; MRSC has stricter topology, Region, latency, and feature constraints. Select the model from measured RPO/RTO and consistency requirements rather than assuming all multi-Region replication is asynchronous.

Pattern 6: Database connection management for Lambda

Critical pattern to avoid connection exhaustion under high concurrency. For the Lambda-side concurrency controls, see Lambda Best Practices.

Why this pattern?

Lambda can create many short-lived execution environments while a relational database has a finite connection budget. Scale-out can therefore open more simultaneous sessions than max_connections permits. A larger database class can increase available resources, but it does not eliminate the need to budget concurrency, reuse valid connections, and bound the backend pool. RDS Proxy can multiplex unpinned client sessions and cap its database connection use; pinned sessions and a saturated database still constrain throughput.

Trade-off

Connection reuse across invocations is opportunistic, not guaranteed — a connection held in global scope only survives if the execution environment is reused, so under highly variable or spiky traffic a meaningful fraction of invocations still pay the connection-establishment cost, and stale connections held across long idle periods can fail silently on the next query. RDS Proxy closes that gap but becomes another component whose pool size, idle timeout, and failover behavior have to be tuned against the actual concurrency profile — it shifts the problem rather than making connection management a non-issue.

Connection lifecycle comparison

How connection handling differs between Lambda connecting directly to RDS versus through RDS Proxy.

AspectWithout ProxyWith RDS Proxy

Lambda SnapStart

For supported Java, Python, and .NET managed Lambda runtimes, SnapStart can reduce initialization latency by restoring a cached snapshot. It is available only for published versions and has feature/runtime constraints.

Caveat

Do not assume a snapshotted database connection remains usable: validate or re-establish network connections after restore, using runtime-specific restore hooks where appropriate. Measure the result; SnapStart does not guarantee a particular millisecond latency.

When to use RDS Proxy

  • Use when measured Lambda concurrency and database connection demand can exceed the safe database connection budget
  • Use for Aurora failover support
  • Use when connection establishment time impacts latency
  • Don't use when direct, reused connections or the RDS Data API meet the concurrency and latency requirements more simply

Pattern 7: SQS + database transactional outbox

Ensuring reliable at-least-once publication from a database transaction. This is the database-specific instance of the event-driven publication patterns covered in Event-Driven Patterns.

Why this pattern?

The failure scenarios the transactional outbox pattern is designed to eliminate.

ProblemSolution
Database write succeeds, message publish failsThe atomically written outbox record persists and the stream processor retries
Message publish succeeds, database write failsTransaction rolls back, no orphaned message
Consumer processes before database commitOutbox only published after transaction completes

Outbox processor example

The order mutation and outbox insert must be one TransactWriteItems operation. The publisher below can send the same message more than once if it crashes after SQS accepts the message but before the stream checkpoint advances.

At-least-once, not exactly-once

Give the event a stable ID in its envelope and make consumers idempotent; the outbox pattern does not create exactly-once delivery. Configure the event source mapping with ReportBatchItemFailures and an on-failure destination.

import os
import boto3

sqs = boto3.client('sqs')
dynamodb = boto3.resource('dynamodb')
outbox_table = dynamodb.Table('outbox')

def lambda_handler(event, context):
    failures = []

    for record in event['Records']:
        image = record.get('dynamodb', {}).get('NewImage')
        if record['eventName'] not in ('INSERT', 'MODIFY') or not image:
            continue
        if image.get('status', {}).get('S') != 'PENDING':
            continue

        outbox_id = image['id']['S']
        event_data = image['event_data']['S']

        try:
            sqs.send_message(
                QueueUrl=os.environ['QUEUE_URL'],
                MessageBody=event_data
            )
        except Exception as exc:
            print(f"Failed to publish {outbox_id}: {exc}")
            failures.append({
                'itemIdentifier': record['dynamodb']['SequenceNumber']
            })
            continue

        # Status is useful for operations/TTL cleanup, but the stream checkpoint—not
        # this status update—is what drives source-record retries.
        try:
            outbox_table.update_item(
                Key={'id': outbox_id},
                UpdateExpression='SET #status = :published',
                ConditionExpression='#status = :pending',
                ExpressionAttributeNames={'#status': 'status'},
                ExpressionAttributeValues={
                    ':pending': 'PENDING',
                    ':published': 'PUBLISHED'
                }
            )
        except Exception as exc:
            # The SQS publish already succeeded. Retrying this source record solely
            # for a status-write failure would create another delivery.
            print(f"Published {outbox_id}; status update needs reconciliation: {exc}")

    return {'batchItemFailures': failures}

When to use the outbox pattern

  • Use when you need atomic business-data/outbox persistence and reliable at-least-once publication
  • Use for event sourcing with reliable downstream notification
  • Don't use for simple fire-and-forget — direct SQS send is simpler
